# SiegeSense Step 3 — Screen Capture, HUD Reading, Rounds & Death Clips Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** When the player starts **Live Mode**, SiegeSense captures the screen, reads the kill feed, round timer, score and health, and builds the match timeline: rounds, kills, deaths, trades, first blood, time alive and re-peeks. Every death is saved as a clip (10 s before + 2 s after) with the mouse trace. The Live page shows all of it as it happens. A **HUD check** lets the player confirm and adjust where each HUD element is on their screen. Warm-up gains **reaction time**.

**Architecture:**
- A `FrameSource` (dxcam on Windows, a video file for replay, a fake for tests) feeds a `CaptureService` thread. That thread keeps a JPEG ring buffer and hands crops to `HudReader` at ~10 Hz.
- `HudReader` reads each HUD region:
  - **Kill feed:** detects changes, segments lines with OpenCV, recognises the names with RapidOCR (fast mode, no text detection), and gets each name's team colour from its hue.
  - **Timer, score, health:** fast recognition of the digits.
- `RoundTracker` turns readings plus input into a match → round → event timeline.
- `ClipWriter` encodes death clips with PyAV/libx264.
- `LiveService` wires this to the protocol and SQLite, as `WarmupService` does.

**Tech Stack:** Step 1–2 stack, plus engine deps `numpy`, `opencv-python-headless`, `rapidocr` + `onnxruntime` (its models ship inside the package; nothing is downloaded), `rapidfuzz`, `av` (PyAV, libx264), and `dxcam` (Windows only, `sys_platform == 'win32'` marker).

**Spec:** `docs/superpowers/specs/2026-11-01-siegesense-design.md` — build step 3 of §9: §4.3 ScreenCapture, §4.4 HudReader, §4.6 RoundTracker, §4.7 ClipWriter. It also covers the reaction time (§4.5) and re-peek (§4.5) items deferred from step 2, and the HUD check from §6.

## Global Constraints

- **Fair play (§2):**
  - Screen capture only. No game memory or process access.
  - Nothing about enemies is ever displayed live. The Live page shows **your own** events (your kills, your death, round results) and summaries.
  - No overlay content mid-round in Live Mode. The step 2 overlay is Warm-up only.
- **Capture:** 30 fps by default (configurable 20–60). Ring buffer of **15 s**. HUD crops go to HudReader at about **10 Hz** (§4.3).
- **Death confirmation (§4.4):**
  - Confirmed only when two signals agree within 3 s: a kill-feed entry where the player is the victim, plus the dead/spectating state.
  - Here "dead/spectating" means the health region shows no readable health number for ≥ 1 s while the round timer is running.
  - A kill-feed-only death is recorded with `confidence="low"` and is excluded from tips.
- **Trade (§4.6):** a kill within **5 s**.
- **Re-peek (§4.5):** after your kill, your view returns to within **3°** of your yaw at the kill within **3 s**, having first moved **≥ 10°** away.
- **Clips (§4.7):** 10 s before + 2 s after the death, MP4. The input trace is saved alongside as JSON. Disk cap **5 GB**, deleting the oldest first.
- **HUD readings carry confidence (§4.4).** Low-confidence readings are flagged and never used for tips. The HUD light turns amber with "Re-run HUD check".
- **Performance guard (§7):** if processing falls behind, lower the capture fps, then the HUD rate, and tell the player through the capture light.
- **All data stays local (§4.11).**

## Rulings carried in from the spec

- **No reference screenshots yet.** HUD regions are configurable, normalised boxes with best-guess defaults:
  - kill feed: top-right
  - timer and score: top-centre
  - health: bottom-left
  The HUD check (screenshot + draggable boxes + what was read) is how the player fixes them. Every reader is tested on synthetic HUD images rendered with OpenCV. Real-screenshot tuning happens when the owner tests.
- **Headshot icon detection is deferred.** It needs a template cut from a real screenshot. The `headshot` field exists and is always `null` for now.
- **Teams come from the name colour in the kill feed.** The player's team is whichever hue cluster their own name has.
- **Which score is yours:** a profile setting `my_score_side: "left" | "right"`, default `"left"`, set in the HUD check.
- **Prep vs action:**
  - A new round starts when the timer jumps up by more than 10 s.
  - The phase is `prep` if the first value after the jump is ≤ 45 s, otherwise `action`.
  - When prep reaches 0, the phase becomes `action`.
  - The round is over when the score changes, or the timer is unreadable for ≥ 4 s after action started.
- **Reaction time** (Warm-up, beta): a visual change in the centre 20 % of the screen (mean absolute grey difference > 12 between consecutive frames) while the mouse has been still for ≥ 150 ms. Then the first flick that starts within 1 s. Reaction time = flick onset − change time.

## Review Focus

1. **The HUD isn't where we expect** (other resolution, HUD scale, ultrawide). Expect readings with low confidence, an amber HUD light with a fix, no false deaths, and the HUD check showing what was read. → Task 5 `test_wrong_region_low_confidence`, Task 11 `hud check shows readings`.
2. **The kill feed shows the same entry for several seconds**, and the OCR misreads a letter (e.g. `Ash.Maln`). Expect one kill event per entry, and fuzzy matching of your name. → Task 4 `test_entry_deduplicated`, `test_fuzzy_own_name`.
3. **The machine is slower than the game**: capture or OCR falls behind. Expect the performance guard to step the fps down, and the warning to show on the capture light. → Task 6 `test_performance_guard_steps_down`.
4. **The disk fills with clips.** Expect the oldest to be removed above the cap. A failed encode logs and the death is still recorded. → Task 8 `test_disk_cap`, `test_encode_failure_keeps_death`.
5. **Not Windows / capture unavailable.** Expect Live Mode to give a clear error. Warm-up still works without capture (reaction time just stays empty). → Task 9 `test_live_without_capture_errors`, Task 7 `test_warmup_without_capture`.

### Task 4: Kill feed reader

**Files:** `hud/killfeed.py`. Test `test_killfeed.py`.

**Interfaces:**
- `@dataclass KillEntry`: `killer: str`, `victim: str`, `killer_team: Literal["blue","orange","unknown"]`, `victim_team: …`, `headshot: bool | None = None`, `confidence: float`, `line_y: int`.
- `def segment_lines(img) -> list[tuple[int,int]]`: the row bands of the kill feed. Text pixels are those with saturation > 80 or value > 200. Row projection; bands ≥ 8 px tall, merged if the gap is < 3 px.
- `def segment_names(line_img) -> list[tuple[int,int]]`: column runs of *coloured* pixels (saturation > 80), gap-split at > 12 px. It returns the leftmost and rightmost runs as killer and victim; the white icon is ignored.
- `def team_of(name_img) -> Literal["blue","orange","unknown"]`: the median hue of coloured pixels (OpenCV hue 0–179). 90–130 → blue; 5–25 → orange; else unknown.
- `class KillFeedReader(ocr, own_name: str)`:
  - `read(img, t) -> list[KillEntry]` returns **new** entries only.
  - Change detection: skip work when the mean abs diff from the previous crop is < 2.
  - Deduplication: (killer, victim) pairs seen within the last 10 s are not new; names are compared with `rapidfuzz.fuzz.ratio ≥ 85`.
  - `is_me(name) -> bool` uses `fuzz.ratio(name.lower(), own_name.lower()) ≥ 85`.
  - Fallback: if segmentation finds no line but there are ≥ 50 coloured pixels, use `ocr.detect_and_recognize` at most once per 2 s.
